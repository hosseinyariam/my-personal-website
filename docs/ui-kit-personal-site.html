معماری Design Token در پروژه‌های مقیاس‌پذیر

هر سیستم طراحی، پیش از آنکه کتابخانه‌ای از کامپوننت‌ها باشد، قراردادی است بین طراحی و کد. اگر این قرارداد فقط در فایل Figma بماند، دیر یا زود شکسته می‌شود.

در دیبا توکن‌ها را در سه لایه تعریف کردیم: primitive برای مقادیر خام، semantic برای نقش‌ها (مثل accent یا surface) و component برای تصمیم‌های موضعی. نتیجه؟ تغییر برندینگ کل محصول، یک PR یک‌خطی شد — همین کیت هم دقیقاً با همین ساختار ساخته شده است.

توکن، قراردادِ طراحی و کد است؛ هر جا این قرارداد شکسته شود، فرسایشِ سیستم از همان‌جا آغاز می‌شود.

قاعده‌ی ساده‌ای هم داریم: هیچ کامپوننتی حق ندارد مستقیم از توکن primitive استفاده کند؛ همیشه باید از لایه‌ی semantic بخرد. همین یک قاعده، ۸۰٪ ناهماهنگی‌های ما را از بین برد.

tailwind.config.js 
colors: {
  brand: { 500: '#F2542D' },    // primitive
  accent: 'rgb(var(--c-accent))', // semantic
}
